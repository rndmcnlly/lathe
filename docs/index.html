Lathe

Sandbox tools for Open WebUI

Source Admin install
Lathe connects a model in Open WebUI to a Linux sandbox. The model can run commands, edit files, use a persistent Python session, run background shell jobs, and share running services in the browser. An admin installs one Python tool; Lathe provisions and reconnects one Daytona sandbox per user.
System

Four parts, with distinct jobs

Open WebUI

Hosts the conversation, model connection, and Lathe tool code. Open WebUI 0.12+ also coordinates native subagents when enabled.

Lathe

Connects tools to the user's sandbox, manages its lifecycle, and returns results. It does not delegate tasks or manage agents.

Daytona

Hosts the Linux sandbox, filesystem, network policy, and service previews.

Your model

Plans the work and calls tools. Choose a tool-capable model; inspecting images also requires vision support.

This arrangement puts a coding-agent workspace behind a chat interface. It does not make the workspace local or provider-free: Open WebUI, the selected model runtime, and Daytona remain part of the trust boundary.

Native foreground subagents return a result before the parent continues; background subagents let it keep working and return their result later. Open WebUI owns that orchestration. With Lathe, parent and child work in the same user's filesystem, while their Python sessions stay separate.

Working model

Files persist; processes do not

A user returns to the same sandbox across conversations. Files, repositories, and installed packages on its filesystem survive ordinary stops and archives. A new tool call starts the sandbox again when needed.

Running servers, shell processes, and in-memory Python state are lost when the sandbox stops or archives. The default configuration stops an idle sandbox after about 15 minutes and archives it 60 minutes later. Administrators can change these intervals.

Conversation context is separate from sandbox state. Open WebUI handles conversation continuation and compaction; save important project context in workspace files so a new conversation can discover it.

Local file work, Python calculations, and self-contained reports remain useful when sandbox Internet access is restricted. Cloning repositories, fetching data, and installing packages need permitted sources. Open WebUI's model connection is separate from the sandbox's outbound network policy.

Tools

A small interface to the sandbox

bash

Run non-interactive shell commands. Long commands continue in the background.

read · write · edit

Inspect numbered line ranges and make explicit file changes.

glob · grep

Find relevant files and search their contents without reading the whole workspace. These tools need ripgrep, supplied locally or from a reachable source.

view

Inspect sandbox images with a vision-capable model: screenshots, charts, and rendered pages.

interpret

Run Python in a chat-scoped REPL whose variables survive between calls.

expose

Share a running HTTP service with explicit private or public access. The agent starts and checks the service first; Lathe does not install it.

onboard · lathe

Load project instructions and consult the model-facing manual.

destroy

With confirmation, permanently remove the sandbox and its workspace.

Workflows

What to ask for

Users describe the outcome. The model decides which tools to call.

  • Understand existing work “Read the project already in my sandbox and explain its first failing test.”
  • Make a local report “Turn this CSV into a self-contained HTML chart using Python's standard library, then show it privately.”
  • Check in parallel “Have one native background subagent audit the local data while you build the report. Read its saved result before finalizing.”
  • Learn a working procedure “Walk me through starting and checking this service. Once we've tested it together, ask before saving a reusable skill.”
  • Continue elsewhere “Save a project summary in the workspace for our next conversation.”

Editors, terminals, and file browsers are optional applications, not bundled Lathe services. They need an existing installation or an approved, reachable source. An administrator may supply an optional public or intranet agent handbook; none is configured by default. This website is the user overview, not that handbook.

With your approval, a proven procedure can become a skill in the sandbox. Fresh conversations can discover and reuse those saved skills alongside project instructions. Lathe discovers existing skills; it does not install an app catalog or automatically save, regenerate, or overwrite procedures.

Trust and retention

Know where the work goes

  • Sandbox data lives in Daytona. Lathe labels each sandbox with the Open WebUI user's email. Files survive normal stops and archives without an additional persistent volume.
  • User environment variables are credentials entrusted to the agent. Lathe injects them into model-directed shell commands. The model can print them, inspect process environments, or read generated command wrappers. Use scoped, revocable credentials.
  • Choose the preview's access mode. Every HTTP exposure is explicitly public or private. Private previews require the deployment's authentication wrapper and never downgrade to public. Public previews may use a direct signed bearer URL when wrapping is unavailable, where the request permits it. Upstream access defaults to 24 hours; the tool reports wrapper expiry separately. Sharing access does not keep a stopped service or sandbox running.
  • Deletion destroys the workspace. Automatic sandbox deletion is disabled by default, but an admin can change that policy. Export important results or commit them to a remote repository before sandbox destruction.
  • Updates are manual. Open WebUI stores the uploaded copy of lathe.py. An installed deployment does not receive fixes merely because the GitHub repository changed, and Lathe has no built-in update or notification mechanism.
Administration

Install deliberately

Lathe is a single Python file installed as an Open WebUI Tool. It runs inside Open WebUI and receives an account-wide Daytona API key, so administrators should review the source and record the installed version. The installed copy reports it through lathe(manpage="version"); administrators can also inspect the source frontmatter's version: field.

The administrator README covers installation, manual updates, valves, security, and verification. The security policy defines support and explains how to obtain security fixes.
